# Sluice v3.1 Security Hardening Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Harden template rendering and LLM feed processing so untrusted RSS data cannot execute template behavior, override prompts, or persist unsafe model output.

**Architecture:** Add a shared sandbox template renderer with plain-data contexts only. Serialize feed items with JSON for LLM prompts, prefer a messages API, and validate model output through schema and shared text sanitizers before storage.

**Tech Stack:** Python 3.11+, Jinja2 `SandboxedEnvironment`, existing LLM provider adapters, pytest, ruff, ty.

---

### Task 1: Add Shared Sandboxed Template Renderer

**Files:**
- Create: `sluice/core/templates.py`
- Modify: `sluice/dag/stages/executors.py`
- Modify: `sluice/dag/sinks/_impl/email.py`
- Modify: `sluice/dag/sinks/_impl/telegram.py`
- Modify: `sluice/dag/sinks/_impl/feishu.py`
- Modify: `sluice/dag/sinks/_impl/_push_base.py`
- Test: `tests/core/test_templates.py`
- Test: `tests/dag/sinks/test_sink_rendering.py`

**Step 1: Write failing tests**

Assert:

- a malicious Jinja payload cannot access Python internals or call objects;
- rich objects such as `PipelineContext` are rejected unless converted to plain
  dictionaries/lists/scalars first;
- per-surface `TemplateContext` allowlists reject credential-like keys such as
  tokens, passwords, secrets, and API keys;
- direct runtime imports or calls to `jinja2.Template` fail an AST/grep test;
- email, Telegram, Feishu, push, LLM prompt templates, and `RenderExecutor` all
  render through the shared sandbox.

**Step 2: Implement renderer**

Create a `SandboxedEnvironment` wrapper that clears nonessential globals/tests,
allows only reviewed filters, disables callable safety, and accepts only
plain-data context values produced by per-surface `TemplateContext` allowlists.
Use `StrictUndefined` unless a specific existing surface needs compatibility
mode.

**Step 3: Migrate call sites**

Replace direct `jinja2.Template(...).render(...)` usage with the shared renderer.
Keep email HTML sanitization after rendering.

### Task 2: Add LLM Prompt Boundary

**Files:**
- Modify: `sluice/dag/stages/executors.py`
- Modify: `sluice/llm/client.py`
- Modify: `sluice/llm/pool.py`
- Modify: `prompts/score_tag.md`
- Modify: `prompts/summarize_zh.md`
- Modify: `prompts/summarize_score_tag.md`
- Test: `tests/dag/stages/test_llm_prompt_boundary.py`
- Test: `tests/llm/test_client.py`

**Step 1: Write failing tests**

Assert:

- feed text containing `ignore previous instructions`, `]]>`,
  `</feed_item>`, markdown fences, repeated boundary text, and JSON-looking
  payloads remains inside a JSON-serialized data object;
- instructions never include raw feed text by string concatenation;
- providers that support messages receive system/developer instructions and
  user JSON separately;
- providers without messages use the documented degraded single-prompt fallback
  with `json.dumps(feed_item)`, a length-prefixed JSON payload, and an explicit
  risk flag.

**Step 2: Implement prompt builder**

Add a prompt builder that returns messages when the provider supports them and a
length-prefixed single-prompt fallback otherwise. Existing prompt files hold
instructions and schema text only; untrusted feed fields are injected only as
serialized JSON. The fallback is not production-preferred and must be marked as
degraded compatibility.

### Task 3: Validate LLM Output and Sanitize Text

**Files:**
- Create: `sluice/core/text_safety.py`
- Modify: `sluice/dag/stages/executors.py`
- Test: `tests/core/test_text_safety.py`
- Test: `tests/dag/stages/test_llm_output_validation.py`

**Step 1: Write failing tests**

Assert:

- scores outside the configured range fail validation by default;
- compatibility clamp mode clamps and records a validation error;
- tags allow only Unicode letters/numbers plus `_`, `-`, `.`, and enforce count
  and length caps;
- tags with control characters, brackets, parentheses, separators, `@`, `<`,
  `>`, or `&` are rejected or normalized according to the allowlist;
- summaries enforce length caps, reject raw HTML tokens and dangerous HTML
  attributes, and reject Markdown links/images with non-allowlisted URL schemes;
- JSON repair returning a scalar is rejected before storage.

**Step 2: Implement schema gate**

Parse model output into a typed result object. Validate `score`, `tags`, and
`summary` before writing DB state. Add a shared sanitizer for Markdown/HTML text
with scheme allowlist `http`, `https`, `mailto`, and sink-supported relative
URLs.

**Step 1: Write failing tests**

Assert `runtime_core = "v3"` cannot be marked production-ready unless v3.1

**Step 2: Implement and document gate**

`security_hardening_pending = true` until sandboxed templates, prompt boundary,
and output validation are active. Document that such runs are not production
eligible. Treat this as a v3 release blocker: without this task merged, operators
must not production-enable `runtime_core = "v3"`.
